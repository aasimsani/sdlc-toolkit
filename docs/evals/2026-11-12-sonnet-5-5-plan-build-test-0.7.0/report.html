### Phase 1 — CSV output
Facts about the code today: `bin/invoices` is POSIX sh. It parses `--status` in a `while`/`case` loop, then runs one inline `awk -F '\t'` program over the TSV. The rule `NR == 1 || status == "" || $4 == status` keeps the header line and the matching rows, and `printf` lays them out as a table. Row 1 of `data/invoices.tsv` is the header (`id customer amount status`).

1. Before changing any code, capture the table output: `sh bin/invoices list > tests/golden/list.txt`. Commit it with the first test. This is the characterization test for AC4 and it passes from the start.
2. In `bin/invoices`, add `--csv) csv=1; shift ;;` to the option loop, with `csv=0` initialised next to `status=""`. Add `[--csv]` to the usage text in the comment and in the error message.
3. After option parsing, branch on `csv`. When `csv` is `1`, run a second awk program with `-F '\t'` and the same `-v status="$status"`. It uses the same rule, `NR == 1 || status == "" || $4 == status`, and the action `{ print $1 "," $2 "," $3 "," $4 }`. Row 1 is the header, so it prints `id,customer,amount,status` through the same path and needs no special case. When `csv` is `0`, run the existing awk program unchanged.
4. Print `$3` as it is. Never add `+ 0` or any arithmetic to it. `CLAUDE.md` says amounts are decimal strings, and awk keeps `4500.00` intact only while it treats the field as a string.
5. This phase leaves fields unquoted, so `Acme, Inc.` comes out as two cells. That is expected until phase 2.

### Phase 2 — Quoting
1. Create `lib/csv.awk` with one function:
   ```awk
   function csv_field(s) {
     if (s ~ /[",]/) { gsub(/"/, "\"\"", s); return "\"" s "\"" }
     return s
   }
   ```
2. In the CSV branch of `bin/invoices`, change the action to `{ print csv_field($1) "," csv_field($2) "," csv_field($3) "," csv_field($4) }`.
3. Load the function without a second program file. Build one program text and pass it to awk once: `prog="$(cat "$root/lib/csv.awk"; printf '%s\n' '<the rule and action>')"`, then `awk -F '\t' -v status="$status" "$prog" "$data"`. This is one plain awk program, so it behaves the same on every POSIX awk. This departs slightly from the RFC's wording ("`awk -f` with two program files"). The `-f` form needs the main program in a file too, and the RFC's fallback to option B exists because of exactly that doubt. If Lee prefers `-f`, the cost is moving the CSV rule into a small file next to `lib/csv.awk`.
4. Every field goes through `csv_field`, the header included, so the header stays `id,customer,amount,status`.

## Tests
Build writes each Build test before the code it tests. Test writes the final tests, which need the whole feature.

Chosen without the testing toolkit, which isn't installed on this machine. Re-run `testing-toolkit:testing` on this plan if Lee wants its choice compared with this one.

- Scenario: a small command-line tool gains one output mode. The risk sits in the output bytes: the CSV layout, the quoting, and the unchanged table. Every check runs the real `bin/invoices` against data and compares its output, so the tests are integration-level by nature, and a separate unit test of `csv_field` would run the same code through the same awk. Done when: each of AC1–AC5 has a passing test, `sh verify.sh` ends with `N passed, 0 failed`, and the AC4 test fails if one byte of the table output changes.
- Left out: unit test of `csv_field` on its own — `csv_field` is one function in one awk file, and AC3 already exercises it through the command.
- Left out: property test and fuzz — the quoting rule is two cases that the spec pins with examples, and the TSV input can't hold a newline or a tab inside a field.
- Left out: contract and end-to-end browser or spreadsheet checks — the only consumer is a spreadsheet opening a file, and RFC 4180 compliance is covered by AC3.
- Left out: mutation testing — no mutation tool exists for shell and awk, and AC3 and AC4 are written to fail on the likely mutations (no quoting, no doubling, changed table).

Notes for whoever writes the tests:
- Write the checks as small shell functions in `tests/test_csv.sh` instead of long `eval` strings. The AC3 rows contain both quote characters, which is awkward to put in the single-quoted string that `check` evaluates. For example: `has_line() { bin/invoices list --csv | grep -Fx -- "$1" >/dev/null; }`, then `check "..." 'has_line "INV-002,\"Acme, Inc.\",310.50,paid"'`.
- `.test-log` and `.verify-last` are gitignored. Don't commit them.

## What could break that the tests won't catch
- **Amount mangled by a float conversion.** AC3's `4500.00` row would catch `4500`, but only if the test compares the whole line. The test must use `grep -Fx` or `cmp` on full lines, not a count.
- **A real data file the sample doesn't represent.** Real exports may contain Windows line endings (a `\r` on the last field) or a customer name with a newline. The spec doesn't cover either, so no test does. If Finance's file has CRLF endings, the status column will carry a `\r`. Worth a question to Lee, and not a change to this plan.
- **Riskiest step: loading `lib/csv.awk` in phase 2.** The function is trivial, and the loading is the part that can differ between awk implementations (macOS awk, mawk and gawk). Run `sh verify.sh` once under the CI image's awk before PR 2 merges. That is the RFC's own stated fallback trigger.
- **`root` and the path to `lib/csv.awk`.** The script already computes `root` from `$0`, so `bin/invoices` works from any directory. Use `"$root/lib/csv.awk"` and never a relative path.

## Size check (ponytail ladder)
- `lib/csv.awk`: needed for the quoting, and the RFC chose a separate file so other commands can reuse it. Inline would be smaller, but the approved RFC decided otherwise. Kept.
- `tests/golden/list.txt`: kept. The AC4 criterion says "the same bytes", and only a golden file proves that.
- `tests/perf_csv.sh`: kept. AC5 requires a timing check, and `verify.sh` should stay fast.
- No new dependency, no new config option, no new class. The `--csv` flag is the only new option and the spec requires it. The header goes through the same path as the rows, so no header special case exists.
