2. Write the failing tests in `tests/test_csv.sh` (sourcing `tests/lib.sh` and using `check`, like `tests/test_list.sh`):
   - AC1: the first line is exactly `id,customer,amount,status`, there are 5 lines in all, and the `INV-001` line is exactly `INV-001,Northwind Traders,1200.00,open`. Do not assert on the `INV-002` or `INV-004` lines here, because phase 2 changes them.
   - AC2: `--status open --csv` and `--csv --status open` (either order) print the header and 3 rows, and none of them contains `,paid`.
3. In `bin/invoices`, add `--csv) csv=1; shift ;;` to the option loop, with `csv=""` set before it. In the awk call, keep the filter condition (`NR == 1 || status == "" || $4 == status`). Pass `-v csv="$csv"` and branch the print: when `csv` is set, `printf "%s,%s,%s,%s\n", $1, $2, $3, $4`, otherwise the existing `printf "%-8s ..."` line, unchanged. Row 1 of the data file is the header `id customer amount status`, so it prints as the CSV header with no special case.
4. Run `sh verify.sh`. All checks, including the AC4 pin, pass.

Ships as PR 1.

### Phase 2 — Quoting
Goal: fields with a comma or a double quote are quoted as RFC 4180 describes.

1. Write the failing test in `tests/test_csv.sh` for AC3. The output of `bin/invoices list --csv` contains the lines `INV-002,"Acme, Inc.",310.50,paid` and `INV-004,"Initech ""West""",4500.00,open` (use `grep -Fx`). Watch it fail, because phase 1 prints these fields unquoted.
2. Create `lib/csv.awk` holding only:
   ```awk
   function csv_field(s) {
     if (s ~ /[",]/) { gsub(/"/, "\"\"", s); return "\"" s "\"" }
     return s
   }
   ```
3. Load it in `bin/invoices`. Plain `awk -f lib/csv.awk` cannot also take the inline program in `bin/invoices`: once `-f` is used, awk treats the next argument as a data file, not as a program. So read the library into the program text instead: `awk ... "$(cat "$root/lib/csv.awk")
   $prog" "$data"`, where `prog` is the existing inline program held in a shell variable (single-quoted). The function is defined before the rules, which every awk accepts. This keeps the RFC's design (the function lives in `lib/csv.awk`) and needs no second `-f`. It's a mechanism detail the RFC didn't spell out, so flag it for Lee in review. If it misbehaves on the CI image, fall back to the RFC's option B (function inline).
4. In the CSV branch, print `csv_field($1)`, `csv_field($2)`, `csv_field($3)`, `csv_field($4)` joined by commas. Leave the table branch alone.
5. Run `sh verify.sh`. The AC1 and AC2 tests from phase 1 and the AC4 pin still pass.

Ships as PR 2.

- Risk: the tests can't catch a different `awk` on another machine or on the CI image (BSD awk on macOS, mawk or gawk on Linux). The riskiest step is phase 2's step 3, loading the library into the program text. Run `sh verify.sh` on the CI image's awk before PR 2 merges, and use the RFC's fallback if it fails.

No fixture file is added (AC4 uses an inline expected string), no dependency, no config option.

# RFC: Holds on gift vouchers

Status: draft

## Problem and goal
A till deducts a voucher at once, and a failed card payment then needs a refund by hand. The goal is a hold that a till captures when the sale completes, and that gives its value back when it isn't captured.

## Constraints
- Every till in a shop is its own process, and they share one SQLite file.
- A sale can take longer than ten minutes when the customer pays the rest by card.

## Options
| Option | Verdict |
|---|---|
| A. Hold, then capture, with a sweeper that releases expired holds | Chosen. |
| B. Deduct at once and refund by hand when the sale fails | Rejected. It is today's behaviour. |
| C. One long database transaction for each sale | Rejected. SQLite allows one writer, so one slow sale would block every till. |

## Chosen solution
Two tables hold the state. `vouchers` has `code`, `face_value`, `available` and `captured`. `holds` has `id`, `code`, `amount`, `state` and `expires_at`. A hold's state is `live`, `captured` or `released`.

1. **Hold.** In one transaction, the till reads the voucher's `available`. If it covers the amount, the till subtracts the amount from `available` and inserts a `live` hold that expires in ten minutes.
2. **Capture.** When the sale completes, in one transaction, the till runs `UPDATE holds SET state = 'captured' WHERE id = ? AND state = 'live'`. Only if that changes one row, it adds the hold's amount to the voucher's `captured` in the same transaction. If it changes no row, the hold was already released or captured, and the capture is refused: nothing is added, and the till must place a new hold (which can be refused) or fail the sale.
3. **Sweeper.** A job runs every minute. For each `live` hold whose `expires_at` has passed, in one transaction, it runs `UPDATE holds SET state = 'released' WHERE id = ? AND state = 'live'`. Only if that changes one row, it adds the hold's amount back to the voucher's `available`.

A hold's amount is counted in exactly one place: in `available` before the hold, held back while the hold is `live`, in `captured` once captured, and back in `available` once released. A capture needs the hold to be `live`, so a hold that the sweeper released can't be captured. Because of that, the total captured against a voucher never exceeds its face value. This holds when two tills use the same voucher at once, and when a hold expires while its sale is still in progress (that sale's capture is refused if the sweeper got there first).

The first draft captured by the hold's id without checking its state. The design check found the failure: till A holds 3 of 5, the hold expires, the sweeper gives the 3 back, till A's slow sale then captures the released hold (captured 3), till B holds 3 and captures (captured 6 on a face value of 5). `fv/design/CaptureByIdOnly.cfg` keeps that design as a config that must fail.

- Before approval (Sam, Lee): when a capture is refused because the hold expired, does the till re-hold and retry, or fail the sale? The spec's R2 and R3 don't say. The design only guarantees that a refused capture adds nothing.
- Before approval (Sam): the spec's acceptance criteria have no test for a capture on a released hold. Add AC6 to `spec.md`, or cover it in the Phase 1 tests as the replay of `fv/design/CaptureByIdOnly.cfg`.

# RFC: Holds on gift vouchers

Status: draft

## Problem and goal
A till deducts a voucher at once, and a failed card payment then needs a refund by hand. The goal is a hold that a till captures when the sale completes, and that gives its value back when it isn't captured.

## Constraints
- Every till in a shop is its own process, and they share one SQLite file.
- A sale can take longer than ten minutes when the customer pays the rest by card. Its capture is then refused (step 2), which is a decision for Lee to confirm: R3 says an uncaptured hold is released after ten minutes, and R4 outranks a sale that outlasts its hold.

## Options
| Option | Verdict |
|---|---|
| A. Hold, then capture, with a sweeper that releases expired holds | Chosen. |
| B. Deduct at once and refund by hand when the sale fails | Rejected. It is today's behaviour. |
| C. One long database transaction for each sale | Rejected. SQLite allows one writer, so one slow sale would block every till. |

## Chosen solution
Two tables hold the state. `vouchers` has `code`, `face_value`, `available` and `captured`. `holds` has `id`, `code`, `amount`, `state` and `expires_at`. A hold's state is `live`, `captured` or `released`.

1. **Hold.** In one transaction, the till reads the voucher's `available`. If it covers the amount, the till subtracts the amount from `available` and inserts a `live` hold that expires in ten minutes.
2. **Capture.** When the sale completes, in one transaction, the till runs `UPDATE holds SET state = 'captured' WHERE id = ? AND state = 'live' AND expires_at > now`. Only if that changed one row, it adds the hold's amount to the voucher's `captured`. If it changed none, the capture is refused and `captured` doesn't change. The till then has to settle the sale another way, such as asking the customer to pay the rest by card or a new hold.
3. **Sweeper.** A job runs every minute. For each `live` hold whose `expires_at` has passed, in one transaction, it adds the hold's amount back to the voucher's `available` and sets the hold's state to `released`.

Every hold reserves its amount before any capture, and a hold can be captured only once and only while it is `live`. The sweeper returns a hold's amount to `available` only when it releases that hold, and a released hold can never be captured, so each amount is either reserved or available, never both. The total captured against a voucher therefore never exceeds its face value. This holds when two tills use the same voucher at once, and when a hold expires while its sale is still in progress: that sale's capture is refused.

The design was checked with a model (`fv/design/`). The first draft of step 2 captured by id with no state check. The model found that a hold can then be released by the sweeper, its amount held by a second till, and the first hold still captured, so `captured` reaches 3 on a voucher worth 2. A capture that checks only "not yet captured" fails the same way.

## Fallback
If the sweeper causes lock contention, run it every five minutes.

### Finding 2 — `place_hold`'s availability check reads a stale value (breaks property 1 independently of Finding 1)

**What goes wrong, and for whom:** `place_hold()`'s `SELECT available ...`
is not inside a transaction (SQLite opens one lazily, on the first write
statement). Two tills can both read the same `available` value before
either writes. The gate `if available < amount` is decided from that read;
the later `UPDATE vouchers SET available = available - ?` computes against
the live column, so neither write is lost, but the gate that was supposed to
stop the second till never re-checks after the first till's write commits.
Both tills can pass the gate for money that only exists once. If both go on
to capture their (over-committed) holds, `captured` exceeds the face value
without `capture()`'s own bug ever coming into it.

**Steps, in order:**

1. `store.issue(db, "GIFT-1", 5000)`
2. Till 1: `SELECT available` — `vouchers/store.py:28` — reads 5000
3. Till 2: `SELECT available` — `vouchers/store.py:28` — also reads 5000 (till 1 has not written yet)
4. Till 1: `UPDATE ... SET available = available - 5000` — `vouchers/store.py:31` — commits, `available` = 0
5. Till 1 captures its hold — `captured` = 5000
6. Till 2: `UPDATE ... SET available = available - 5000` — `vouchers/store.py:31` — this is a fresh read of the column at write time (0), so `available` becomes **-5000**, not rejected
7. Till 2 captures its hold — `captured` = 10000, on a voucher worth 5000

**Disposition:** reproduced, for the `available`-goes-negative half (the
exact SQL `place_hold()` issues, run from two separate `sqlite3`

## What this pass leaves open

- **Sizes.** 2 tills, one voucher, a hold amount equal to the face value, at
  most 2 place-hold cycles per till and at most 2 `capture()` calls per
  cycle. A third till, a third retry, or amounts that only partially
  exhaust the voucher were not run.
- **Time.** `TimeExpires` is a nondeterministic step, not a real clock
  reaching `HOLD_SECONDS` (600s). The ten-minute figure itself (R3's "ten
  minutes") is not checked by this model; only the ordering of expiry
  against capture is.
- **Hold identity.** The model gives each till one reusable hold slot; a
  second `place_hold` call overwrites it rather than allocating a new
  auto-increment id, unlike the real `INSERT`. This does not affect either
  safety invariant, which never keys on hold id, but a property that did
  depend on distinct ids per hold would need a different model.
- **No crash fault, no message loss.** Both findings come from statement
  ordering inside one process (SQLite's lazy transaction start), not from a
  process dying mid-operation or a message being lost or duplicated at the
  network layer. A crash between `UPDATE holds SET state='captured'` and
  `UPDATE vouchers SET captured = captured + ?` (`store.py:46-47`, two
  separate statements inside one `with db:` block, so one SQLite
  transaction either both lands or neither does on a clean crash, but a
  crash mid-write-ahead-log could still be worth its own check) was not
  modelled.
- **The real place_hold race was reproduced at the SQL level, not through
  two real OS threads calling `place_hold()` with an injected delay.** The
  statements are identical and the order matches the model's trace exactly,
  but a thread-level reproduction would be stronger evidence and would also
  double as a regression test, which this check does not add.
- **Non-functional requirement** ("placing a hold and capturing one each
  take under 50 ms") is outside this check's scope entirely.
- **The `available`-never-negative conservation law** (`NeverOverAvailable`)
  was only checked as holding on the fixed design; it was not separately
  isolated per-race the way the two confirmed properties were, since
  Finding 2's reproduction already demonstrates it breaking under the real
  race by a stronger route.

### Finding 1 — `capture()` can be applied twice to the same hold (breaks property 1)

**What goes wrong, and for whom:** `capture()` reads a hold's amount by id
and unconditionally writes `state = 'captured'` and `captured += amount`. It
never checks that the hold is still `'live'`. A second call on the same hold
— a retried request from a till after a timeout, or a delayed completion
that lands after a `sweep()` has already released the hold — adds the
amount to `captured` again. The shop ends up believing more money was
captured against the voucher than it is worth; property 1 ("the total
captured against a voucher never exceeds its face value") breaks.

**Steps, in order:**

1. `store.issue(db, "GIFT-1", 5000)` — `vouchers/store.py:20-22`
2. `hold = store.place_hold(db, "GIFT-1", 5000, now=0)` — `vouchers/store.py:25-36`, `available` becomes 0
3. `store.capture(db, hold)` — `vouchers/store.py:39-48`, `captured` becomes 5000
4. `store.capture(db, hold)` again (retry, or a late completion) — `vouchers/store.py:46-47` write unconditionally again, `captured` becomes 10000 > face value 5000

## What this pass leaves open

- **Sizes.** 2 tills, one voucher, a hold amount equal to the face value, at
  most 2 place-hold cycles per till and at most 2 `capture()` calls per

  exhaust the voucher were not run.

- **Hold identity.** The model gives each till one reusable hold slot; a

  auto-increment id, unlike the real `INSERT`. This does not affect either
  safety invariant, which never keys on hold id, but a property that did

- **Non-functional requirement** ("placing a hold and capturing one each

- **The `available`-never-negative conservation law** (`NeverOverAvailable`)
